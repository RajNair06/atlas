How atlas actually works

One Go binary, one YAML file, ~4,000 lines of code. Here is every moving part and why it exists.

Life of a failing request

  1. Arrival. The correlation middleware stamps the request with an X-Request-ID (generated at the edge if absent) and logs it. The ID rides along to every upstream and appears in every log line and history entry.
  2. Forwarding. The proxy looks up the exact path in the route table, rebuilds the request (method, headers, buffered body), and sends it with the route's timeout.
  3. Failure. Either the upstream answers 4xx/5xx, or the transport itself fails (connection refused, timeout). Both paths converge: the proxy captures a FailedRequest — method, path, upstream, status, error body, headers, timing, the route's fallback — into the error store.
  4. Breaker check. The per-upstream circuit breaker is consulted first. If it's open, healing fast-fails in microseconds: no LLM call, no retries, no cost.
  5. Analysis. Gemini receives a structured prompt (full context + a closed menu of three actions + few-shot examples) and must answer with strict JSON: {action, reasoning, fallback_path?}. The response is validated — unknown actions, missing reasoning, or fallbacks without a path are rejected. If Gemini is unreachable, a deterministic rule engine decides instead, and the reasoning string discloses the degradation.
  6. The gate. With approval mode on, a PendingDecision is published to the console over SSE and the executor blocks. The client's request hangs — deliberately — until a human approves, rejects, or the approval timeout expires. The latency budget starts after approval: human think-time never eats the machine budget.
  7. Execution. Retry: replays with exponential backoff (100 → 200 → 400ms), stopping at the first sub-400 response, the budget, or the attempt cap. If retries exhaust and the route has a fallback, one last-resort fallback attempt runs. Fallback: replays against the configured fallback base URL. Give-up: returns the original error untouched.
  8. Response. Healed? The client receives the healed response plus X-Healed, X-Healing-Action, X-Healing-Attempts. Not healed? The original error, byte-for-byte. Either way the outcome lands in the console history — gated and ungated alike.

Circuit breaker states

            failure #N (N = threshold)
   CLOSED ─────────────────────────────> OPEN
     ▲                                     │  fast-fail: no LLM, no retries (~2ms)
     │  trial succeeds                     │
     │                                     ▼  reset window elapses
     └────────────────────────────── HALF-OPEN
              trial fails ──> re-OPEN     │
                                          └─ admits exactly ONE trial request

Breakers are per-upstream-URL and live in memory. Their job is threefold: protect a dying service from retry storms, protect your LLM bill from pointless analysis, and protect clients from waiting on doomed requests.

Design decisions worth defending

Why synchronous healing (the client waits)?

Because the alternative — return the error now, heal in the background — doesn't heal this request; it just decorates its failure. Blocking with an approval timeout gives the request a real chance to succeed while bounding the worst case. The tradeoff (a parked connection during approval) is explicit, and the budget system keeps the machine-time portion tight.

Why human approval at all?

An LLM classifying errors is fallible; retrying a non-idempotent POST against a half-dead payment service can double-charge. The gate makes a human the circuit's final breaker. It's toggleable at runtime precisely so teams can start gated and loosen as trust accumulates — with every decision audited either way.

Why exact-match routing?

Simplicity with zero ambiguity. Wildcards, prefix trees, and regex routes are a well-trodden path — atlas deliberately spends its complexity budget on healing, not matching. Exact match is also trivially auditable: what you configure is exactly what routes.

Why a rule-based fallback brain?

Born from reality: during development, Google's free tier hit a demand spike (503s across every flash model) and the whole healing pipeline went dark. A self-healing gateway whose brain dies on someone else's outage is a contradiction. The rule engine mirrors the prompt's guidance in code, keeps the console fed, and always discloses itself in the reasoning. Degradation is a first-class state, not a crash.

Why Go templates + htmx instead of a SPA?

The console ships inside the same binary (templates are go:embed-ed). No Node, no bundler, no asset pipeline — one go build produces the entire product. SSE + htmx partial swaps give genuine real-time behavior; the whole UI is a few hundred lines of HTML anyone can read.

Testing philosophy

  • Interfaces at every seam. Analyzer, RequestReplayer, Approver, AutoRecorder — production wires the real implementations; tests wire fakes. No network, no LLM bills, no flake.
  • Full-stack E2E without leaving the process. The proxy suite drives the real ServeHTTP against real executors and fake upstreams: heals, rejections, expiries, breaker trips, body integrity, transport failures.
  • Timing assertions, not hope. Backoff tests assert elapsed time; breaker tests use wide windows so the race detector can't flake them.
  • Race detector on everything. CI runs go vet + go test -race on every push.
